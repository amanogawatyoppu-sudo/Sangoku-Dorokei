# Meshy 自動リギング版 SOL 試験導入（ローカルプレイヤー1体のみ）

`TRI_TRACE_SOL_rig_test_package.zip` の `TRI_TRACE_SOL_60k_rig_experimental.glb`（と 40k 版）を、ローカルプレイヤー1体だけに切り替えられるようにした。**採用判定はしていない**。v9.1 本体は旧キャラのまま（既定オフ）。

## 使い方
- `?glb=meshy`（60k）／`?glb=meshy40`（40k）／`?glb=1`（前回の剛体試作）／`?glb=0`（必ず旧キャラ）
- モデルは `public/characters/` の外部ファイル。**オンのときだけ取得**し、オフのときはダウンロードしない
  - 前回の試作 GLB もページへの同梱をやめた。ページは 1535 → 1214 kB
- 読み込みに失敗したら旧キャラのまま
- CPU・オンラインの他プレイヤー・NPC は旧キャラのまま

## 事前調査（HEAD cd1ee4d、ブランチ v9.1-glb-test）
- テスト 40ファイル 307件 合格、ビルド成功（1535 kB）
- 前回の仕組みを再利用: 旧キャラを見えないリグとして残し、見た目だけを差し替える。座標・当たり判定・TRACE・速度・役職秘匿・同期は旧キャラ側のまま
- GLB の中身
  - 1スキンメッシュ（60,000三角形／47,276頂点）、19関節、6クリップ
  - PBRマテリアル1つ、2048²の JPEG テクスチャ3枚（色／法線／粗さ。金属度はほぼ0）
  - 法線データなし
  - Hips の移動は Y（上下の揺れ）だけ。X・Z の移動はない

## 実装（`src/render/meshyCharacter.ts`）
- 足元 Y≈−0.95・身長 1.87 を、**親グループだけ**で持ち上げ・拡大し、旧プレイヤーと同じ高さ（46.5）に合わせた。GLB 本体には触れていない
- 前方は +Z でゲームと一致（顔は前、バックパックは後ろ。テストで確認）。回転の補正は不要
- ルートモーションなし: 念のため Hips の X・Z の移動を0に固定。移動は従来のシミュレーションのまま
- クリップの切り替えは前回の `ClipPlayer` を共通化して使用（0.2 秒のクロスフェード、歩幅に合わせた再生速度）
- 法線がないので滑らかな法線を計算した。色テクスチャはゲームの色の扱い（カラーマネジメントなし）に合わせた
- 勢力色: テクスチャは SOL の橙で、塗り替えられない
  - そのため **SOL として表示されているときだけ** Meshy を使う
  - LUNA・STAR に配属された場合や、別勢力に変装中は旧キャラ（正しい色）に戻る
- 建物の陰でのシルエット（x-ray）は旧キャラのものを残した（6万三角形をもう一度描かないため）
- 確認用の `?debug` フック: `glb()`（状態）、`glbTrace()`、`glbHold(clip, t)`（姿勢を止めて撮影する）

## 実画像で確認した結果
- **良い点**
  - 後方カメラで橙のフードとバックパックがはっきり見え、SOL だと分かる（前回の剛体試作より勢力が読みやすい）
  - 夜も橙のフードは見える
  - 足は地面に接している
  - バックパックは潰れず、走っても胴体と一緒に動く
  - 膝の潰れ・貫通は見られなかった（ただし曲げ角が小さいため）
- **関節・変形の問題（大きい順）**
  1. **足の滑り**
     - 1周期で足首が進む距離: Walk 6.4 / Run 10.0 / Sprint 11.8 ゲーム単位
     - その間に体が進む距離: Walk 約86 / Run 約108 / Sprint 約132 単位
     - **約10倍足りず、足が地面を滑る**。再生速度では直せない（周期が非現実的に速くなる）。クリップの脚の振り幅を大きくする必要がある
  2. **脚の動きが小さい**
     - 太ももの振り: Sprint で ±19°（旧キャラは約 ±54°）
     - 膝の曲げ: 最大 32°（旧キャラは約 110°）
     - 走っていても後方カメラからは「歩いている」程度に見える
  3. **腕がほとんど振れない**
     - 袖が胴と一体のメッシュのため、腕を回すと上着ごと変形する
     - TRACE で右腕を上げると、右袖が胴へ食い込んで凸凹になる（`5-joints-trace.jpg`）
  4. **脚のオレンジのストラップが棒状に伸びる**
     - 走りの蹴り出しで後ろへ伸びる（`3-` `4-` の横・位相1/3）
     - 太ももとすねの重みが混ざる部分の自動ウェイトが原因と思われる
  5. **後ろに残る脚の裾が引き伸ばされる**（横から、位相3）
  6. **TRACE の動きが小さい**: 胴のひねりは約 8°、右腕は 56° で、通常カメラでは分かりにくい
- 正面の顔は暗く、フードの影で表情が読みにくい
- 急旋回（走行中）は Sprint のまま。その場の旋回だけ Turn

## 性能（本番ビルド、HIGH、1366×768、同じ10地点、SOL 配属）
| | 旧キャラ | Meshy 60k | Meshy 40k | 剛体試作 |
|---|---|---|---|---|
| 描画呼び出し（平均） | 227.9 | 224.3 | 224.4 | 226.5 |
| 三角形（平均） | 141,111 | 196,456（+5.5万） | 176,040（+3.5万） | 161,262 |
| テクスチャ | 82.6 MB | **146.6 MB（+64 MB）** | 146.6 MB | 82.6 MB |
| 頂点・インデックス | 11.6 MB | 14.8 MB | 14.1 MB | 13.5 MB |
| fps（CPU描画・参考） | 2.54 | 1.96 | 2.25 | 2.47 |
| 取得するファイル | — | 3.9 MB | 3.2 MB | 0.25 MB |

- 三角形は本体と影の2回分。描画呼び出しは変わらない（差は CPU 人物の位置による誤差の範囲）
- **実GPUは使えない**（SwiftShader の CPU 描画）。fps は参考値で、GPU の性能ではない
  - CPU描画では Meshy 60k で約23%遅くなった（6万三角形のスキン変形と影の分）
  - 実機では `?debug&glb=meshy` で開き、`__sangoku.frameStats()` を実行すると測れる
- テクスチャ +64 MB（2048² × 3枚）は、スマホでは重い。採用するなら 1024² に縮小（約 −48 MB）、影は簡易形状で落とす、遠景用の LOD を用意する、などが必要
- 全員に広げた場合の目安: 1人あたり +6万三角形 × 2回（本体と影）。今回は広げていない

## テスト・回帰
- テスト 41ファイル 315件 合格（新規 `tests/meshyCharacter.test.ts` 8件）
  - 19関節・6クリップ、ルートモーションなし、親グループでの接地と身長、全クリップで足が地面より下に沈まない／頂点が飛び出さない、+Z 向き、SOL 以外は使わない、クリップの切り替え
- ビルド成功（1214 kB と、モデルファイル）
- 実ゲーム（本番ビルド、Meshy オン／オフ）: 背後からの TRACE → LOCK POINT、階段（同じ速さで上る）、会議は両方とも同じ
- 敵の役職隠し・ANCHOR の変装・CPU 戦のランダム配属・オンライン同期: 見た目の差し替えだけで、判定と同期のデータは触っていない。変装時は旧キャラの塗り分けに戻る

## まとめ
- 統合の仕組み（切り替え・遅延読み込み・失敗時の戻り・接地・向き・6クリップ）は動いている
- 見た目は後方カメラで魅力が出ている
- ただし**足の滑り（約10倍）、脚・腕の振りの小ささ、ストラップと袖の変形**があり、このままの採用は勧めない
- 次は Blender などで、脚と腕の振り幅（特に Run/Sprint）、肩・肘・股・ストラップのウェイトを手直しする必要がある
- 性能面では、テクスチャ 2048²×3 の縮小が先に必要
